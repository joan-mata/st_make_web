✅ Buenas Prácticas

Escribir código que funcione es solo el primer paso. El objetivo profesional es escribir código que cualquier persona (incluido tú mismo dentro de seis meses) pueda leer, mantener y ampliar sin esfuerzo.

1. ¿Por qué importan las buenas prácticas?

En el mundo real, el código se escribe una vez pero se lee decenas de veces: para corregir errores, añadir funciones, hacer revisiones de código. Un código mal organizado ralentiza al equipo entero y genera más errores.

  • Mantenibilidad: es fácil corregir errores y añadir funciones.
  • Escalabilidad: el proyecto puede crecer sin reescribirse desde cero.
  • Trabajo en equipo: cualquier compañero puede entender el código sin preguntar.
  • Menos errores: el código limpio y predecible tiene menos bugs.
📌 La regla del Boy Scout "Deja el código un poco mejor de como lo encontraste." Cada vez que tocas un archivo, aprovecha para mejorar pequeñas cosas: renombrar una variable confusa, extraer una función, añadir un comentario útil.

2. DRY — Don't Repeat Yourself

El principio más importante: si un bloque de código aparece más de una vez, conviértelo en una función. Cuando hay que corregir un bug o cambiar la lógica, solo se toca un lugar, no diez.

⚠️ Incorrecto — código repetido (WET: "Write Everything Twice") 
<?php
// ❌ MAL: la misma lógica de conexión copiada en cada archivo

// En pagina1.php:
$pdo1 = new PDO('pgsql:host=localhost;dbname=tienda', 'postgres', '1234');
$pdo1->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

// En pagina2.php:
$pdo2 = new PDO('pgsql:host=localhost;dbname=tienda', 'postgres', '1234');
$pdo2->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

// En pagina3.php:
$pdo3 = new PDO('pgsql:host=localhost;dbname=tienda', 'postgres', '1234');
$pdo3->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

// ❌ MAL: si cambias la contraseña, tienes que cambiarlo en 10 sitios
// y seguro que te olvidas alguno.
✅ Correcto — DRY: una función, un lugar 
<?php
// ✅ BIEN: la lógica está en un único lugar

// config/database.php
function getConexion(): PDO {
    static $pdo = null;  // singleton: crear la conexión solo una vez
    if ($pdo === null) {
        $dsn  = "pgsql:host=" . getenv('DB_HOST') . ";dbname=" . getenv('DB_NAME');
        $pdo  = new PDO($dsn, getenv('DB_USER'), getenv('DB_PASSWORD'), [
            PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        ]);
    }
    return $pdo;
}

// En cualquier archivo:
require_once 'config/database.php';
$pdo = getConexion();  // siempre la misma función, siempre la misma lógica

DRY en HTML con includes

<?php
// ❌ MAL: el header y footer copiados en cada página
// pagina1.php, pagina2.php, pagina3.php... todos con el mismo <header> copy-paste

// ✅ BIEN: el header y footer están en archivos separados
// includes/header.php
// includes/footer.php

// En cada página:
require_once 'includes/header.php';
// ... contenido específico de la página ...
require_once 'includes/footer.php';

// Si cambias el menú de navegación, solo lo cambias en un archivo.
?>

3. Nombres descriptivos

El código se escribe para que lo lean personas, no solo máquinas. Los nombres de variables, funciones y archivos deben describir qué contienen o qué hacen, sin necesidad de comentarios adicionales.

⚠️ Nombres confusos — ¿qué hace esto? 
<?php
// ❌ MAL: nombres de una letra o sin significado
$x   = 22;
$d   = new DateTime();
$arr = getUserData();

function f($a, $b) {
    return $a * $b * 0.21;
}

$r = f(100, 3);  // ¿qué es r? ¿qué hace f? ¿qué significan 100 y 3?
✅ Nombres claros — el código se lee como texto 
<?php
// ✅ BIEN: nombres que explican qué son y qué hacen
$edadUsuario       = 22;
$fechaRegistro     = new DateTime();
$datosUsuario      = getUserData();

/**
 * Calcula el IVA de un importe dado.
 * @param float $importeBase  Importe sin IVA
 * @param int   $cantidadItems  Número de artículos
 * @return float Total con IVA incluido
 */
function calcularTotalConIVA(float $importeBase, int $cantidadItems): float {
    $tasaIVA     = 0.21;   // IVA estándar en España
    $subtotal    = $importeBase * $cantidadItems;
    $importeIVA  = $subtotal * $tasaIVA;
    return $subtotal + $importeIVA;
}

$totalPedido = calcularTotalConIVA(importeBase: 100.0, cantidadItems: 3);

4. Una función = una responsabilidad

El Principio de Responsabilidad Única (SRP, del inglés Single Responsibility Principle) dice que cada función debe hacer una sola cosa y hacerla bien. Las funciones pequeñas y enfocadas son más fáciles de probar, depurar y reutilizar.

⚠️ Función "monstruo" — hace demasiadas cosas a la vez 
<?php
// ❌ MAL: esta función valida, conecta a la BD, inserta Y envía un email.
// Si falla el email, ¿qué pasa con el registro? Imposible de probar.
function procesarRegistroUsuario($datos) {
    // Validación
    if (empty($datos['email'])) return false;
    if (strlen($datos['password']) < 8) return false;

    // Conexión a la BD
    $pdo = new PDO('pgsql:host=localhost...', 'user', 'pass');

    // Inserción
    $stmt = $pdo->prepare("INSERT INTO usuarios...");
    $stmt->execute([...]);
    $id = $stmt->fetchColumn();

    // Envío de email de bienvenida
    mail($datos['email'], "Bienvenido", "Gracias por registrarte...");

    return $id;
}
✅ Correcto — cada función tiene una sola responsabilidad 
<?php
// ✅ BIEN: funciones pequeñas, cada una con un único propósito

function validarDatosRegistro(array $datos): array {
    $errores = [];
    if (empty($datos['email']) || !filter_var($datos['email'], FILTER_VALIDATE_EMAIL)) {
        $errores[] = 'Email no válido.';
    }
    if (strlen($datos['password'] ?? '') < 8) {
        $errores[] = 'La contraseña debe tener al menos 8 caracteres.';
    }
    return $errores;  // array vacío = sin errores
}

function crearUsuario(PDO $pdo, string $nombre, string $email, string $hash): int {
    $stmt = $pdo->prepare(
        "INSERT INTO usuarios (nombre, email, password_hash) VALUES (:n, :e, :h) RETURNING id"
    );
    $stmt->execute([':n' => $nombre, ':e' => $email, ':h' => $hash]);
    return (int)$stmt->fetchColumn();
}

function enviarEmailBienvenida(string $email, string $nombre): void {
    $asunto  = "Bienvenido, $nombre";
    $mensaje = "Gracias por registrarte en nuestro sitio.";
    mail($email, $asunto, $mensaje);
}

// Uso: cada función se puede probar y depurar por separado
$errores = validarDatosRegistro($_POST);
if (empty($errores)) {
    $pdo     = getConexion();
    $hash    = password_hash($_POST['password'], PASSWORD_BCRYPT);
    $nuevoId = crearUsuario($pdo, $_POST['nombre'], $_POST['email'], $hash);
    enviarEmailBienvenida($_POST['email'], $_POST['nombre']);
}

5. Comentarios útiles

Los buenos comentarios explican el por qué de una decisión, no el qué hace el código (eso ya se ve leyendo el código). El código bien nombrado casi no necesita comentarios.

⚠️ Comentarios inútiles — repiten lo que ya dice el código 
<?php
// ❌ MAL: comentarios que no aportan información
$i = 0;              // inicializar i a 0
$i++;                // incrementar i
$usuarios = [];      // array de usuarios
// Bucle para recorrer usuarios
foreach ($usuarios as $usuario) {
    // imprimir nombre
    echo $usuario['nombre'];
}
✅ Comentarios que explican el "por qué" y el contexto 
<?php
// ✅ BIEN: los comentarios aportan contexto que el código solo no puede dar

// Usamos BCRYPT con coste 12 (en lugar del 10 por defecto) porque
// los servidores de producción son suficientemente potentes y
// queremos mayor resistencia a ataques de fuerza bruta.
$hash = password_hash($password, PASSWORD_BCRYPT, ['cost' => 12]);

// Redirigir ANTES de mostrar nada (Post/Redirect/Get pattern).
// Sin esto, si el usuario recarga la página, el formulario se reenvía.
header('Location: ' . BASE_URL . '/dashboard');
exit;  // exit es obligatorio después de header('Location:...')

// La consulta excluye registros con deleted_at IS NOT NULL (borrado lógico).
// Ver ARCHITECTURE.md para la decisión de no usar borrado físico.
$stmt = $pdo->query("SELECT * FROM productos WHERE deleted_at IS NULL");

7. Control de versiones con Git

Git es la herramienta que permite guardar el historial completo de cambios del proyecto, trabajar en equipo sin pisar el trabajo de los demás, y recuperar cualquier versión anterior del código. 

# Iniciar un repositorio Git en el proyecto
git init

# Ver el estado actual (qué archivos han cambiado)
git status

# Añadir archivos al área de preparación (staging)
git add config/database.php          # un archivo específico
git add controllers/                  # una carpeta entera
git add .                             # todo (con cuidado: asegúrate que .gitignore está correcto)

# Crear un commit con un mensaje descriptivo
git commit -m "feat: añadir función de registro de usuarios con validación"

# Ver el historial de commits
git log --oneline

# Subir los cambios al repositorio remoto (GitHub)
git push origin main

Mensajes de commit descriptivos

Un buen mensaje de commit explica QUÉ cambió y POR QUÉ, no cómo.

⚠️ Mensajes de commit inútiles 
git commit -m "cambios"
git commit -m "arreglos"
git commit -m "wip"
git commit -m "asdfgh"
✅ Mensajes de commit claros 
git commit -m "feat: implementar login con verificación de contraseña bcrypt"
git commit -m "fix: corregir error de codificación UTF-8 en nombres con acentos"
git commit -m "refactor: extraer lógica de validación a función separada"
git commit -m "docs: añadir comentarios al fichero de conexión a BD"
git commit -m "security: usar prepared statements en consulta de búsqueda"
📌 Convención: Conventional Commits Prefijos comunes: feat: (nueva función), fix: (corrección), refactor: (mejora sin cambio de funcionalidad), docs: (documentación), style: (formato), test: (pruebas), security: (seguridad).

8. Separación de responsabilidades

Cada tecnología tiene su función específica. Mezclarlas crea código espagueti difícil de mantener.

TecnologíaResponsabilidadLo que NO debe hacer
HTML Estructura y contenido del documento Dar estilos (atributos style, bgcolor)
CSS Presentación visual y diseño Lógica de negocio o manipulación de datos
JavaScript Comportamiento e interactividad en el navegador Acceder directamente a la base de datos
PHP Lógica de servidor, procesamiento, autenticación Mezclar lógica y HTML en el mismo archivo (sin MVC)
SQL Almacenamiento y consulta de datos Lógica de negocio compleja (reglas de negocio van en PHP)

9. Manejo de errores

Los errores siempre ocurren: la base de datos no responde, el archivo no existe, el usuario envía datos incorrectos. El buen código los gestiona; el código descuidado los ignora hasta que causan un fallo en producción.

⚠️ Errores ignorados — comportamiento impredecible 
<?php
// ❌ MAL: si la conexión falla, el código sigue y da errores extraños más adelante
$pdo = new PDO('pgsql:host=localhost;dbname=tienda', 'user', 'pass');
$stmt = $pdo->query("SELECT * FROM usuarios");  // puede fallar silenciosamente
$usuarios = $stmt->fetchAll();  // $stmt puede ser false
✅ Manejo explícito de errores con try/catch 
<?php
// ✅ BIEN: los errores se detectan y gestionan de forma controlada
try {
    $pdo = getConexion();  // lanza PDOException si falla
    $stmt = $pdo->prepare("SELECT * FROM usuarios WHERE id = :id");
    $stmt->execute([':id' => $id]);
    $usuario = $stmt->fetch();

    if ($usuario === false) {
        // El usuario no existe: redirigir con mensaje informativo
        header('Location: usuarios.php?error=not_found');
        exit;
    }
} catch (PDOException $e) {
    // Error de base de datos: loggear el detalle técnico, mostrar mensaje genérico
    error_log('[Error BD] ' . $e->getMessage() . ' en ' . $e->getFile() . ':' . $e->getLine());
    // Nunca mostrar el mensaje técnico al usuario en producción
    http_response_code(500);
    die("Ha ocurrido un error interno. Por favor, inténtalo más tarde.");
}
📌 Desarrollo vs Producción En desarrollo: muestra todos los errores (display_errors = On en php.ini) para depurar más rápido.
En producción: oculta los errores al usuario pero regístralos en el log (display_errors = Off, log_errors = On). Mostrar errores técnicos al usuario en producción es un riesgo de seguridad.

10. Seguridad como hábito

La seguridad no es un módulo que se añade al final del proyecto. Es una mentalidad que se aplica en cada decisión de diseño:

  • ¿Este dato viene del usuario? → Validar y sanitizar.
  • ¿Voy a mostrarlo en HTML? → htmlspecialchars().
  • ¿Voy a usarlo en SQL? → Prepared statement.
  • ¿Es una contraseña? → password_hash().
  • ¿Es una credencial? → Variable de entorno, nunca en el código.
  • ¿Es un formulario POST? → Token CSRF.

Consulta la guía de Seguridad para ejemplos completos de cada uno de estos puntos.

Resumen: checklist de buenas prácticas

  • Aplicar el principio DRY: si se repite más de dos veces, hacer una función.
  • Usar nombres descriptivos para variables, funciones y archivos.
  • Cada función tiene una sola responsabilidad clara.
  • Los comentarios explican el por qué, no el qué.
  • Estructura de archivos lógica y predecible.
  • Usar Git con commits frecuentes y mensajes descriptivos.
  • Separar HTML / CSS / JS / PHP / SQL en sus responsabilidades.
  • Gestionar todos los errores con try/catch y logs.
  • Practicar la seguridad en cada línea que toca datos externos.

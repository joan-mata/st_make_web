📊 UML y Diagramas ER

Antes de escribir una sola línea de SQL, necesitas un plano. Los diagramas Entidad-Relación (ER) y los diagramas de clases UML son ese plano: te permiten diseñar la estructura de tu base de datos y tu código con claridad, antes de que cambiar algo cueste horas de refactorización.

1. ¿Por qué diseñar antes de programar?

Imagina que vas a construir una casa. No empezarías a colocar ladrillos sin tener primero los planos del arquitecto. Sin planos, las paredes pueden no cuadrar, las habitaciones pueden quedar mal distribuidas, y cambiar algo implica tirar lo que ya está hecho.

Con las bases de datos ocurre exactamente lo mismo. Si empiezas a crear tablas directamente en PostgreSQL sin haberlo diseñado antes, es muy probable que acabes con:

  • Datos redundantes: el mismo dato repetido en múltiples tablas.
  • Relaciones rotas: claves foráneas que no apuntan a ningún lado.
  • Tablas demasiado grandes: una tabla que debería ser tres.
  • Refactorizaciones dolorosas: cambiar una columna implica modificar 10 scripts PHP.
✅ La regla de oro Dibuja el diagrama primero. Aunque sea en papel y a mano. Cinco minutos diseñando te pueden ahorrar horas de correcciones.

Un buen diseño de base de datos también facilita el trabajo en equipo: cuando todos los miembros ven el mismo diagrama, todo el mundo sabe qué tabla hace qué y cómo se relacionan.

2. Diagrama Entidad-Relación (ER)

El Diagrama Entidad-Relación (o diagrama ER) es el método más usado para modelar bases de datos relacionales. Fue propuesto por Peter Chen en 1976 y sigue siendo el estándar hoy en día.

Los tres conceptos fundamentales

ConceptoRepresentaciónEn la base de datosEjemplo
Entidad Rectángulo Una tabla usuarios, productos, pedidos
Atributo Óvalo Una columna de la tabla nombre, email, precio
Relación Rombo Clave foránea (FK) "un usuario realiza muchos pedidos"

Cardinalidad

La cardinalidad indica cuántas instancias de una entidad se relacionan con cuántas instancias de otra. Hay tres tipos:

TipoNotaciónEjemplo
Uno a uno (1:1) 1 ─── 1 Un usuario tiene un perfil. Un perfil pertenece a un usuario.
Uno a muchos (1:N) 1 ─── N Un usuario tiene muchos pedidos. Un pedido pertenece a un usuario.
Muchos a muchos (N:M) N ─── M Un pedido tiene muchos productos. Un producto aparece en muchos pedidos.
📌 N:M siempre necesita una tabla intermedia Una relación muchos a muchos no se puede representar directamente con claves foráneas. Necesita una tabla de unión (también llamada tabla puente o junction table) que contiene las FKs de ambas tablas.

🔑 id (PK)
🔗 usuario_id (FK)

Diagrama simplificado: usuarios (1) → (N) pedidos (N) ↔ (M) productos. La relación N:M entre pedidos y productos requiere una tabla intermedia detalle_pedido.

3. Ejemplo práctico completo

Vamos a diseñar la base de datos de una pequeña tienda online. Primero el diagrama, luego el SQL.

Paso 1: El diagrama

usuarios
🔑 id SERIAL PK
nombre VARCHAR(100)
email VARCHAR(150)
contraseña_hash TEXT
1 ↓ N
pedidos
🔑 id SERIAL PK
🔗 usuario_id FK → usuarios
fecha TIMESTAMP
estado VARCHAR(20)
1 ↓ N
detalle_pedido (unión N:M)
🔑 id SERIAL PK
🔗 pedido_id FK → pedidos
🔗 producto_id FK → productos
cantidad INTEGER
N ↓ 1
productos
🔑 id SERIAL PK
nombre VARCHAR(200)
precio DECIMAL(10,2)

Paso 2: El SQL (viene DESPUÉS del diagrama)

-- 1. Primero, la tabla sin dependencias externas
CREATE TABLE usuarios (
    id               SERIAL PRIMARY KEY,
    nombre           VARCHAR(100) NOT NULL,
    email            VARCHAR(150) UNIQUE NOT NULL,
    contrasena_hash  TEXT NOT NULL,
    creado_en        TIMESTAMP DEFAULT NOW()
);

-- 2. Luego la tabla de productos (tampoco tiene FKs aún)
CREATE TABLE productos (
    id       SERIAL PRIMARY KEY,
    nombre   VARCHAR(200) NOT NULL,
    precio   DECIMAL(10, 2) NOT NULL CHECK (precio >= 0),
    stock    INTEGER DEFAULT 0 CHECK (stock >= 0)
);

-- 3. Ahora pedidos (depende de usuarios → se crea después)
CREATE TABLE pedidos (
    id          SERIAL PRIMARY KEY,
    usuario_id  INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
    fecha       TIMESTAMP DEFAULT NOW(),
    estado      VARCHAR(20) DEFAULT 'pendiente'
                    CHECK (estado IN ('pendiente','pagado','enviado','cancelado'))
);

-- 4. La tabla de unión se crea al final (depende de las otras dos)
CREATE TABLE detalle_pedido (
    id          SERIAL PRIMARY KEY,
    pedido_id   INTEGER NOT NULL REFERENCES pedidos(id)   ON DELETE CASCADE,
    producto_id INTEGER NOT NULL REFERENCES productos(id) ON DELETE RESTRICT,
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unit DECIMAL(10, 2) NOT NULL  -- precio en el momento de la compra
);
💡 El orden importa Las tablas con claves foráneas deben crearse DESPUÉS de las tablas a las que apuntan. Por eso pedidos se crea después de usuarios, y detalle_pedido se crea la última.

4. Tipos de relaciones

Relación 1:1 — Uno a uno

Una instancia de la entidad A se relaciona con exactamente una instancia de la entidad B, y viceversa.

1

🔑 id PK
🔗 usuario_id FK UNIQUE

CREATE TABLE perfiles (
    id          SERIAL PRIMARY KEY,
    usuario_id  INTEGER UNIQUE NOT NULL REFERENCES usuarios(id),
    -- UNIQUE garantiza que solo puede haber un perfil por usuario
    biografia   TEXT,
    avatar_url  VARCHAR(255)
);

Relación 1:N — Uno a muchos

Una instancia de A puede relacionarse con muchas instancias de B, pero cada instancia de B solo pertenece a una instancia de A. Es el tipo de relación más común.

La clave foránea siempre va en el lado del "muchos" (N). En el ejemplo, usuario_id está en la tabla pedidos porque un pedido pertenece a un usuario (no al revés).

Muchas instancias de A se relacionan con muchas instancias de B. En bases de datos relacionales, esta relación no se puede representar directamente — necesita una tabla de unión que contiene las FKs de ambas tablas.

5. UML de Clases para MVC

El diagrama de clases UML se usa para modelar la capa de modelos de una arquitectura MVC. Cada caja representa una clase PHP con sus atributos (propiedades) y métodos.

Caja de clase UML

Una caja de clase UML tiene tres secciones:

Usuario
- id: int
- nombre: string
- email: string
- contraseñaHash: string
+ __construct(nombre, email)
+ getById(id): Usuario
+ guardar(): bool
+ eliminar(): bool

Sección 1: Nombre de la clase

Sección 2: Atributos (propiedades). El símbolo - indica privado, + público, # protegido.

Sección 3: Métodos. El tipo de retorno va después de :.

Código PHP correspondiente

-- El diagrama UML de la clase Usuario
-- se corresponde con esta tabla SQL:

CREATE TABLE usuarios (
    id              SERIAL PRIMARY KEY,
    nombre          VARCHAR(100) NOT NULL,
    email           VARCHAR(150) UNIQUE NOT NULL,
    contrasena_hash TEXT NOT NULL
);
💡 UML y ER son complementarios El diagrama ER describe la base de datos. El diagrama de clases UML describe el código PHP. En una app bien diseñada, cada tabla del ER suele corresponder a una clase PHP en la carpeta models/.

💡 Prueba dbdiagram.io Entra en dbdiagram.io y escribe esto en el editor: 
Table usuarios {
  id integer [pk, increment]
  nombre varchar
  email varchar [unique]
}

Table pedidos {
  id integer [pk, increment]
  usuario_id integer [ref: > usuarios.id]
  fecha timestamp
}
El diagrama se genera automáticamente a la derecha. Puedes exportarlo como imagen.

7. Del diagrama al código

Aquí está el proceso completo, paso a paso, para ir de un enunciado de problema hasta el código SQL y PHP funcional.

Ejemplo: "Construye una app de gestión de tareas para equipos"

PasoAcciónResultado
1 Identifica las entidades (sustantivos del enunciado) usuarios, equipos, tareas
2 Identifica los atributos de cada entidad usuarios: nombre, email
equipos: nombre, descripcion
tareas: titulo, descripcion, estado, fecha_limite
3 Identifica las relaciones (verbos del enunciado) un usuario pertenece a un equipo (1:N)
una tarea es asignada a un usuario (1:N)
una tarea pertenece a un equipo (1:N)
4 Decide las cardinalidades ¿Puede un usuario pertenecer a varios equipos? → entonces es N:M
5 Dibuja el diagrama En draw.io o dbdiagram.io, con todas las tablas y flechas
6 Escribe las sentencias CREATE TABLE en SQL Primero las tablas sin FKs, luego las que tienen FKs
7 Escribe el código PHP (Models) Una clase PHP por cada tabla, con métodos CRUD
📌 El diagrama puede evolucionar No pasa nada si el diagrama cambia a medida que avanzas en el desarrollo. Lo importante es que SIEMPRE refleje el estado actual de la base de datos. Si cambias una tabla, actualiza el diagrama. Trátalo como documentación viva.
✅ Resumen del proceso Análisis → Diagrama ER → SQL → PHP. En ese orden. Nunca empieces por el código. El diagrama es el contrato entre el diseño y la implementación.

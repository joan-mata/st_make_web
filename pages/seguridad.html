🔒 Seguridad

La seguridad no es una opción ni algo que se añade al final. Es un hábito que se practica desde la primera línea de código. Aquí verás los ataques más comunes y cómo prevenirlos.

1. ¿Por qué importa la seguridad?

La organización OWASP (Open Web Application Security Project) publica cada pocos años el OWASP Top 10: la lista de los diez riesgos de seguridad más críticos en aplicaciones web. Los primeros puestos están ocupados consistentemente por ataques que se previenen con buenas prácticas básicas de programación.

2. Nunca credenciales en el código

El error más frecuente de los desarrolladores principiantes es escribir contraseñas, claves API y tokens directamente en el código fuente. Si ese código llega a un repositorio público (o incluso privado mal configurado), las credenciales quedan expuestas.

⚠️ Incorrecto — credenciales en el código fuente 
<?php
// ❌ MAL: contraseña en texto plano en el código
// Si este archivo se sube a GitHub, cualquiera tiene acceso total a la BD
$pdo = new PDO(
    'pgsql:host=localhost;dbname=tienda',
    'postgres',
    'mi-contrasena-secreta'
);

// ❌ MAL: clave de API externa en el código
$api_key = 'clave-externa-secreta-hardcoded'; // ← visible para todos
✅ Correcto — variables de entorno con .env 
# .env  ← este archivo NUNCA se sube a Git (añádelo a .gitignore)
DB_HOST=localhost
DB_NAME=tienda
DB_USER=postgres
DB_PASSWORD=mi-contrasena-secreta
SERVICIO_API_KEY=clave-externa-secreta
<?php
// ✅ BIEN: se leen de variables de entorno, no están en el código
$pass    = getenv('DB_PASSWORD');
$api_key = getenv('SERVICIO_API_KEY');

Proteger el .env con .gitignore

Lo más importante: añade .env a tu .gitignore antes de hacer el primer commit. 

# .gitignore
.env
.env.local
.env.production
vendor/
*.log
⚠️ Si ya subiste el .env a Git Borrarlo del repositorio no es suficiente: el historial de commits guarda el contenido antiguo. Debes revocar y regenerar todas las credenciales expuestas inmediatamente.

3. SQL Injection

La inyección SQL ocurre cuando datos introducidos por el usuario se concatenan directamente en una consulta SQL, permitiendo al atacante modificar la lógica de la consulta.

⚠️ Código vulnerable — NUNCA hagas esto 
<?php
// ❌ VULNERABLE: los datos del usuario se pegan directamente en el SQL
$email    = $_POST['email'];     // atacante escribe: ' OR '1'='1
$password = $_POST['password'];  // atacante escribe: cualquier_cosa

// La consulta resultante sería:
// SELECT * FROM usuarios WHERE email = '' OR '1'='1' AND password = 'x'
// '1'='1' siempre es TRUE → el atacante entra sin contraseña válida
$query = "SELECT * FROM usuarios WHERE email = '$email' AND password = '$password'";
$result = $pdo->query($query);  // ¡VULNERABLE!
✅ Código seguro — Prepared Statements (siempre) 
<?php
// ✅ SEGURO: PDO separa el SQL del dato, imposible inyectar
$email    = $_POST['email'];
$password = $_POST['password'];

// Los :email y :password son marcadores de posición (placeholders)
// PDO los envía al motor de BD por separado, nunca como SQL
$stmt = $pdo->prepare("SELECT * FROM usuarios WHERE email = :email");
$stmt->execute([':email' => $email]);
$usuario = $stmt->fetch();

// Verificar la contraseña contra el hash almacenado
if ($usuario && password_verify($password, $usuario['password_hash'])) {
    echo "Login correcto. Bienvenido, " . htmlspecialchars($usuario['nombre']);
} else {
    echo "Email o contraseña incorrectos.";  // nunca decir cuál de los dos
}

Con los prepared statements, PDO separa completamente el SQL del dato. Aunque el atacante escriba ' OR '1'='1, ese valor se trata literalmente como una cadena de texto y nunca es interpretado como SQL.

4. XSS — Cross-Site Scripting

XSS ocurre cuando la aplicación muestra en la página HTML datos introducidos por el usuario sin escaparlos. El atacante puede inyectar código JavaScript malicioso que se ejecuta en el navegador de otros usuarios: robar cookies de sesión, redirigir a páginas de phishing, etc.

⚠️ Código vulnerable — inyección de HTML/JS desde la URL 
<?php
// URL de ataque: pagina.php?nombre=<script>alert('XSS')</script>
// ❌ MAL: se imprime directamente sin escapar
$nombre = $_GET['nombre'];
echo "Hola, $nombre";  // ← el JS del atacante se ejecuta en el navegador
✅ Código seguro — htmlspecialchars() siempre que muestres datos de usuario 
<?php
// ✅ BIEN: htmlspecialchars convierte los caracteres especiales en entidades HTML
// < → &lt;   > → &gt;   & → &amp;   " → &quot;   ' → &#039;
$nombre = $_GET['nombre'] ?? '';
echo "Hola, " . htmlspecialchars($nombre, ENT_QUOTES, 'UTF-8');
// Si el atacante envía <script>...</script>, se muestra como texto inofensivo

// Para mostrar datos de la BD también:
echo htmlspecialchars($usuario['nombre'], ENT_QUOTES, 'UTF-8');
📌 Regla sencilla Cada vez que uses echo para mostrar un valor que viene del usuario (formulario, URL, base de datos), envuélvelo en htmlspecialchars(). Sin excepciones.

5. Contraseñas en la base de datos

Nunca, bajo ninguna circunstancia, guardes contraseñas en texto plano en la base de datos. Si alguien accede a la base de datos, obtendría directamente las contraseñas de todos los usuarios.

La solución es el hashing: una función matemática de un solo sentido que transforma la contraseña en una cadena irreversible. PHP incluye password_hash() con bcrypt, que es el estándar actual.

⚠️ Incorrecto — contraseña en texto plano o con MD5/SHA1 
<?php
// ❌ MAL: texto plano
$stmt->execute([':pass' => $password]);

// ❌ MAL: MD5 o SHA1 son algoritmos rotos para contraseñas
$stmt->execute([':pass' => md5($password)]);
$stmt->execute([':pass' => sha1($password)]);
✅ Correcto — password_hash() con bcrypt 
<?php
// ════════════════════════════════════
// REGISTRO — guardar nueva contraseña
// ════════════════════════════════════
$password = $_POST['password'];

// password_hash genera automáticamente un salt aleatorio
// El resultado es algo como: $2y$10$eImiTXuWVxfM37uY4JANjQ...
$hash = password_hash($password, PASSWORD_BCRYPT);

$stmt = $pdo->prepare(
    "INSERT INTO usuarios (nombre, email, password_hash) VALUES (:n, :e, :h)"
);
$stmt->execute([':n' => $nombre, ':e' => $email, ':h' => $hash]);

// ════════════════════════════════════
// LOGIN — verificar contraseña
// ════════════════════════════════════
$email    = trim($_POST['email']    ?? '');
$password = $_POST['password'] ?? '';

$stmt = $pdo->prepare("SELECT * FROM usuarios WHERE email = :email AND activo = TRUE");
$stmt->execute([':email' => $email]);
$usuario = $stmt->fetch();

// password_verify compara el texto con el hash almacenado
if ($usuario && password_verify($password, $usuario['password_hash'])) {
    // Login correcto: iniciar sesión
    session_start();
    session_regenerate_id(true);  // previene session fixation
    $_SESSION['usuario_id']   = $usuario['id'];
    $_SESSION['usuario_nombre'] = $usuario['nombre'];

    header('Location: dashboard.php');
    exit;
} else {
    $error = "Email o contraseña incorrectos.";
}

6. Validación y sanitización de datos

Validar significa comprobar que el dato tiene el formato correcto (un email válido, un número positivo…). Sanitizar significa limpiar el dato (eliminar espacios, caracteres extraños…). Siempre valida y sanitiza los datos antes de usarlos o guardarlos. 

<?php
// ── Sanitización básica ───────────────────────────────────────
$nombre = trim($_POST['nombre'] ?? '');          // eliminar espacios al inicio/fin
$nombre = strip_tags($nombre);                   // eliminar etiquetas HTML
$email  = trim(strtolower($_POST['email'] ?? '')); // lowercase + trim

// ── Validación con filter_var() ───────────────────────────────
// Email
if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
    $errores[] = "Email no válido.";
}

// URL
if (!filter_var($url, FILTER_VALIDATE_URL)) {
    $errores[] = "URL no válida.";
}

// Número entero (p. ej: ID desde la URL)
$id = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);
if ($id === false || $id === null || $id <= 0) {
    die("ID no válido.");
}

// ── Validaciones manuales ─────────────────────────────────────
if (empty($nombre)) {
    $errores[] = "El nombre es obligatorio.";
} elseif (strlen($nombre) < 2 || strlen($nombre) > 100) {
    $errores[] = "El nombre debe tener entre 2 y 100 caracteres.";
}

// Edad: debe ser numérica y estar en rango
$edad = $_POST['edad'] ?? '';
if (!is_numeric($edad) || (int)$edad < 0 || (int)$edad > 120) {
    $errores[] = "La edad debe ser un número entre 0 y 120.";
}

// ── Castings seguros ─────────────────────────────────────────
$id    = (int)$_GET['id'];          // fuerza a entero (imposible inyección)
$precio = (float)$_POST['precio'];  // fuerza a decimal

7. CSRF — Protección de formularios

Un ataque CSRF (Cross-Site Request Forgery) engaña al navegador del usuario autenticado para que envíe una petición maliciosa a tu aplicación sin que el usuario lo sepa. Por ejemplo: una web maliciosa hace que el navegador de la víctima envíe un formulario de transferencia de dinero.

La defensa estándar es el token CSRF: un valor secreto aleatorio incluido en el formulario que el servidor verifica antes de procesar la petición. 

<?php
// ── Generar el token CSRF (en el controlador que muestra el formulario) ──
session_start();
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));  // 64 caracteres aleatorios
}
$csrfToken = $_SESSION['csrf_token'];
?>

<!-- En el HTML del formulario, incluir el token como campo oculto -->
<form action="procesar.php" method="POST">
  <input type="hidden" name="csrf_token" value="<?= htmlspecialchars($csrfToken) ?>">
  <!-- resto del formulario -->
  <button type="submit">Enviar</button>
</form>
<?php
// ── Verificar el token CSRF en el procesador ──
session_start();

$tokenRecibido = $_POST['csrf_token'] ?? '';
$tokenEsperado = $_SESSION['csrf_token'] ?? '';

// hash_equals previene ataques de tiempo (timing attacks)
if (!hash_equals($tokenEsperado, $tokenRecibido)) {
    http_response_code(403);
    die("Error de seguridad: token CSRF inválido.");
}

// Si llega aquí, la petición es legítima
// Procesar el formulario normalmente...

8. Cabeceras de seguridad HTTP

El servidor puede enviar cabeceras HTTP que indican al navegador cómo comportarse de forma más segura. Son una línea de defensa adicional. 

<?php
// Añadir estas cabeceras al inicio de cada respuesta HTTP
// (o configurarlas en el servidor Apache/Nginx)

// Evita que el navegador cargue tu página dentro de un <iframe>
// (protege contra clickjacking)
header('X-Frame-Options: DENY');

// Evita que el navegador "adivine" el tipo de contenido
header('X-Content-Type-Options: nosniff');

// Política de seguridad de contenido: controla qué recursos se pueden cargar
// (primera línea de defensa contra XSS)
header("Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' cdnjs.cloudflare.com; style-src 'self' 'unsafe-inline' cdnjs.cloudflare.com");

// Fuerza HTTPS (solo si tienes certificado SSL)
header('Strict-Transport-Security: max-age=31536000; includeSubDomains');

// Controla qué información se envía en el header Referer
header('Referrer-Policy: strict-origin-when-cross-origin');
📌 Configuración alternativa en Apache (.htaccess) 
<IfModule mod_headers.c>
    Header always set X-Frame-Options "DENY"
    Header always set X-Content-Type-Options "nosniff"
    Header always set Referrer-Policy "strict-origin-when-cross-origin"
</IfModule>

Resumen: lista de verificación de seguridad

  • Usar prepared statements para todas las consultas SQL con datos del usuario.
  • Usar htmlspecialchars() siempre que se muestren datos del usuario en HTML.
  • Usar password_hash() / password_verify() para contraseñas (nunca texto plano, nunca MD5).
  • Guardar credenciales en variables de entorno (.env), nunca en el código fuente.
  • Añadir .env al .gitignore desde el primer día.
  • Incluir token CSRF en todos los formularios POST.
  • Validar y sanitizar todos los datos de entrada (formularios, URL, cookies).
  • Añadir cabeceras de seguridad HTTP básicas.
  • Usar HTTPS (certificado SSL/TLS) en producción.
  • No mostrar mensajes de error detallados en producción (display_errors = Off en php.ini).
✅ Clave mental Cada dato que llega desde fuera (usuario, URL, BD externa) es potencialmente malicioso. Valídalo, sanitízalo y escápalo antes de usarlo.
